# Project APEX — Master Build Guide

**Status:** Binding project constitution  
**Applies to:** Every human or AI contributor, planning session, implementation, experiment and release  
**Primary objective:** Grow APEX from a deterministic public-data research starter into a defensible, uncertainty-aware, real-world-oriented Formula racing simulator without relying on proprietary team data or the F1 game as the source of truth.

---

## 0. Mandatory instruction to every future builder

Before planning or changing APEX:

1. Read this file completely.
2. Read `SIMULATOR_MATURITY_MODEL.md`.
3. Read the rows relevant to the requested work in `RESEARCH_BACKLOG.csv` and `BUILD_BACKLOG.csv`.
4. Read the linked paper protocol, data contract and source modules.
5. Run the existing tests and at least one relevant reference command.
6. Inspect the generated artifacts rather than trusting a success message.
7. State the current maturity level, the requested target, unmet dependencies and the evidence required for completion.
8. Only then produce a plan or write code.

**Do not begin with UI, Dreamer, Mamba, reinforcement learning, MPC, self-play or a large refactor unless their prerequisite gates are already satisfied.**

A future AI agent must treat this guide as an engineering contract, not optional background reading.

# 1. Project mission

APEX is being built to answer questions of the form:

> Given a vehicle, driver, track, tyres, energy state, weather, race control and the evolving field, what physically feasible futures are plausible, how uncertain are they, and which strategy is best under that uncertainty?

The long-term system should support:

- calibrated single-car lap and stint simulation;
- tyre, fuel and hybrid-energy state evolution;
- full-field stochastic race simulation;
- traffic, dirty air, DRS, overtaking, pits, flags and weather;
- counterfactual race-strategy evaluation;
- exact or optimization-based small-case benchmarks;
- fast adaptive policies and planners;
- explicit uncertainty, abstention and failure reporting;
- comparison across synthetic evidence, public historical data and later game telemetry;
- reproducible research-paper adaptations.

The goal is **not** to claim parity with a confidential team simulator. The target is a research-grade public-data simulator whose strengths, uncertainty and unsupported regions are measurable and honest.

---

# 2. Non-goals

APEX must not become any of the following:

- a visual dashboard wrapped around heuristics;
- an LLM that narrates telemetry without a validated simulation core;
- a one-track overfit model presented as a general simulator;
- a clone of an F1 game physics engine;
- a giant end-to-end neural network with no physical constraints or baselines;
- a collection of disconnected paper implementations;
- a strategy recommender evaluated only on scenarios used for tuning;
- a simulator declared “realistic” because outputs look plausible;
- a repository whose progress is measured by file count, model size or UI polish.

# 3. Authority and conflict resolution

When two project sources conflict, use this order of authority:

1. **This `00_MASTER_BUILD_GUIDE.md`.**
2. **Frozen contracts, laws of the simulated domain and acceptance tests.**
3. **`SIMULATOR_MATURITY_MODEL.md` and backlog dependency fields.**
4. **Pre-registered experiment protocols and paper equation maps.**
5. **Current verified source code and regression tests.**
6. **Subsystem documentation and architecture decision records.**
7. **Textbooks, examples and educational scaffolding.**
8. **Suggestions generated during the current AI or human session.**

A newer idea does not automatically override an older verified contract. Conflicts must be written into an Architecture Decision Record before changing the authoritative behaviour.

External papers are evidence and design inputs, not unquestionable specifications. When a paper conflicts with available data, regulations, dimensional consistency or stronger validation, record the conflict and test it.

---

# 4. Truth labels

Every important value, field, model and result must be labelled as one of:

- **Measured:** directly supplied by a declared source.
- **Reconstructed:** computed from measured data using a documented procedure.
- **Imputed:** filled because source data was missing.
- **Proxy:** a substitute target or state that is not the real measured quantity.
- **Calibrated:** estimated from designated calibration data.
- **Prior:** assumed before observing the target evidence.
- **Simulated:** generated by the APEX engine.
- **Game-derived:** observed from a future game experiment.
- **Unknown:** unsupported or unavailable.

These labels must survive ingestion, feature engineering, training, evaluation and UI display. A proxy must never silently become “ground truth.”

# 5. The evidence hierarchy

APEX decisions should be supported through progressively stronger evidence:

```text
Dimensional consistency and hand calculations
                ↓
Deterministic synthetic invariants
                ↓
Equation-level paper adaptation tests
                ↓
Public-data descriptive calibration
                ↓
Held-out recorded-control replay
                ↓
Closed-loop single-car stability
                ↓
Tyre/fuel/ERS multi-stint validation
                ↓
Stochastic full-field historical replay
                ↓
Optimization and policy regret benchmarks
                ↓
Later game-domain intervention tests
                ↓
Frozen multi-season public benchmark
```

Evidence from a later layer does not excuse a failure in an earlier layer. For example, matching a race result does not validate incorrect units, and matching game telemetry does not prove real-world physical accuracy.

# 7. Maturity ladder and dependency order

The authoritative levels are defined in `SIMULATOR_MATURITY_MODEL.md`. The compact dependency chain is:

```text
R0  deterministic fixtures
 └─► R1  equation-level paper adaptations
      └─► R2  public-data descriptive models
           └─► R3  calibrated single-car replay
                └─► R4  stable closed-loop single car
                     └─► R5  tyre/fuel/ERS race model
                          └─► R6  stochastic full field
                               └─► R7  adaptive strategy system
                                    └─► R8  multi-agent/world-model planning
                                         └─► R9  game-domain validation
                                              └─► R10 research-grade release
```

## 7.1 No level skipping

A feature may be prototyped early in `apexsim.research`, but it cannot influence the production simulator or planner until its prerequisite level is passed.

Examples:

- A tyre neural network can be prototyped at R2, but cannot determine race strategy until tyre state is validated for R5.
- An RL policy can be trained against a toy environment at R1, but cannot be called a race strategist until R6/R7 evidence exists.
- A world model can be explored educationally, but cannot drive an optimizer before closed-loop stability, OOD handling and planner-exploitation tests.
- Future game telemetry cannot promote a component whose public-data and synthetic gates failed.

## 7.2 How to select the next task

When asked to “continue APEX,” “plan the build,” or “start implementing,” the planner must:

1. Filter `RESEARCH_BACKLOG.csv` to the earliest maturity phase containing incomplete P0 work.
2. Remove rows whose `depends_on` requirements are not complete.
3. Prefer tasks that create evidence or unblock several downstream tasks.
4. Select one coherent vertical slice, usually one to three backlog rows.
5. Define a stopping gate before coding.
6. Do not mark a task complete until its acceptance evidence exists in the repository.

At the time this guide was added, the next research-foundation sequence begins with the unresolved R1 equation-fidelity work, including the FIENI symbol-to-code table, hand-calculated transition fixture and tiny exact oracle. The live backlog remains authoritative if statuses later change.

              │                           │                          │

## 8.1 Architectural rule

The final engine is hybrid:

```text
known physical and regulatory structure
+ calibrated empirical relationships
+ probabilistic hidden-state estimation
+ bounded learned residual corrections
+ optimization baselines
+ fast adaptive policies
+ uncertainty-aware fallback behaviour
```

No single paper or model family owns the entire simulator.

## 8.2 Production versus research namespace

- `apexsim.sim_core`: only components that passed their applicable promotion gates.
- `apexsim.research`: paper adaptations, prototypes, proxies and incomplete experiments.
- `tests`: executable contracts and regression evidence.
- `research/protocols`: pre-registered methods, equations, assumptions and evaluation rules.
- `artifacts`: immutable run outputs; not source code.

Moving code from `research` into `sim_core` is a formal promotion, not a file cleanup.

# 9. Subsystem contracts and definitions of done

## 9.1 Data and provenance

A data subsystem is complete only when:

- every source has a versioned manifest, retrieval time, licence note and hash where feasible;
- canonical units and coordinate frames are declared;
- measured, reconstructed, imputed and proxy values are distinguishable;
- event-level splits prevent temporal and session leakage;
- scalers and calibration parameters are fit on training data only;
- an untouched benchmark set is frozen;
- missingness and alignment quality are reported;
- raw source data is never silently overwritten.

## 9.2 Track model

A track reconstruction is complete only when:

- a curvilinear distance coordinate is stable and monotonic;
- the circuit closes within a declared positional tolerance;
- curvature, heading and elevation conventions are documented;
- smoothing does not use future evaluation data improperly;
- start/finish, pit entry, pit exit, sectors and DRS zones are represented;
- uncertainty from sparse/noisy position data is quantified;
- synthetic tracks and reconstructed real tracks share one validated interface.

## 9.3 Vehicle model

A vehicle model is complete for its maturity level only when:

- all forces use documented SI units;
- numerical integration is stable under timestep refinement;
- acceleration, braking and lateral limits obey physical bounds;
- drag, downforce, rolling resistance and mass effects have isolated tests;
- combined longitudinal/lateral demand uses a documented friction constraint;
- parameters have priors, calibration ranges and identifiability analysis;
- held-out section and lap errors beat the declared simple baseline;
- failures are separated by speed, curvature and operating regime.

## 9.4 Tyre model

A tyre subsystem must separate:

- compound identity;
- age;
- temperature states;
- wear/degradation state;
- grip or pace effect;
- four-wheel energy or load proxies;
- wet-weather suitability;
- uncertainty.

It is complete only when:

- pit resets and compound changes are correct;
- thermal and wear updates obey monotonic and conservation-like sanity checks;
- fuel mass, track, driver and weather effects are not confounded without analysis;
- fresh-compound offsets and crossover behaviour are evaluated on held-out stints;
- measured targets are not confused with proxies;
- tree, statistical and physics baselines are included;
- tyre predictions remain stable in multi-lap closed-loop use.

## 9.5 Fuel and hybrid energy

The energy subsystem is complete only when:

- fuel mass decreases consistently with consumption;
- mass affects dynamics and/or lap-time maps through a documented path;
- battery state stays within bounds;
- deployment and harvesting signs are unambiguous;
- terminal fuel and battery feasibility is enforced and logged;
- pit-entry recuperation and sector dependence are tested when implemented;
- an exact or continuous optimizer is available as a benchmark before RL promotion;
- constraint correction is part of the environment contract, not hidden in the policy.

## 9.6 Driver policy

A driver policy is complete only when:

- actions are causal and cannot see future outcomes;
- action ranges are physically feasible;
- a transparent rule-based controller exists as a baseline;
- complete laps can be driven without divergence;
- action perturbations produce directionally correct responses;
- recovery after small disturbances is tested;
- style parameters are separated from car parameters where identifiable;
- an OOD detector and safe fallback are defined before aggressive planning.

## 9.7 Race kernel

A race kernel is complete only when:

- timing, ranking, lap counting and finish classification are deterministic under a fixed seed;
- pit entry, service and exit preserve ordering and time consistently;
- flags and safety-car states obey explicit invariants;
- DRS eligibility, dirty air and overtaking are modular rather than hardcoded into lap time;
- stochastic events are sampled from declared distributions;
- Monte Carlo results converge within a declared budget;
- historical replay errors and distributional statistics are reported;
- impossible states fail loudly.

## 9.8 Learned dynamics and world models

A learned dynamics model is complete only when:

- it competes against persistence, deterministic physics, linear/ridge, tree and state-space baselines as applicable;
- training and evaluation horizons are matched across methods;
- one-step, multi-step open-loop and closed-loop results are all reported;
- seen and unseen tracks/sessions are separate;
- uncertainty or abstention is available;
- learned residual magnitude is bounded or monitored;
- latent-state probes and intervention tests establish what information is represented;
- planner exploitation tests fail before the model can control strategy;
- compute budget and parameter count are disclosed.

## 9.9 Strategy and planning

A strategy component is complete only when:

- the decision variables and observation timing are causal;
- rules and fixed strategies are implemented first;
- tiny instances have an exact enumeration or DP oracle;
- larger cases have the strongest feasible optimization benchmark;
- policy quality is reported as regret, not only reward;
- runtime, constraint violations and robustness to model error are reported;
- nominal and disturbed scenarios are evaluated;
- stochastic strategies are compared through confidence intervals and rank stability;
- no planner is trusted outside the simulator’s validated horizon and support.

## 9.10 User interface

The UI is complete only when:

- every plotted or stated result links to an artifact, model version and data source;
- uncertainty is shown where relevant;
- proxy or simulated values are labelled;
- precision never exceeds evidence quality;
- the UI cannot silently mutate simulation assumptions;
- core experiments can be reproduced without the UI.

# 10. Research-paper implementation protocol

Every paper enters APEX through the following sequence:

```text
1. identify one testable claim
2. freeze the exact paper/version
3. classify work as reproduction, replication or adaptation
4. write a paper card
5. map every used symbol to code, unit and source
6. write one hand-calculated numerical fixture
7. implement the smallest independent equation-level module
8. test bounds, resets, signs and monotonic claims
9. reconstruct a published scenario when evidence permits
10. compare against simpler matched baselines
11. run public-data or synthetic validation
12. document deviations and unsupported variables
13. decide FAIL / INCONCLUSIVE / DIRECTIONAL_MATCH /
    PARTIAL_REPLICATION / REPLICATED_WITHIN_TOLERANCE
14. promote only within the tested domain
```

Use `research/REPLICATION_STANDARD.md` as the detailed authority.

## 10.1 Paper-specific direction already established

- **FIENI strategy work:** joint fuel, battery, tyre wear and pit decisions; exact small-case oracle; optimization-versus-policy regret.
- **Todd tyre-energy work:** four-wheel targets, event-safe forecasting, strong tree baselines, seen/unseen tracks and explanation faithfulness. Current APEX tyre energy is a proxy until a measured target is available.
- **Heilmeier family:** race orchestration, Monte Carlo events and strategy robustness.
- **Perantoni/Limebeer:** minimum-lap-time optimal control and track/vehicle dynamics upgrades.
- **West/Tremlett/Farroni:** thermal and wear dynamics.
- **Duhr:** hybrid energy allocation and MPC.
- **Thomas/Fieni/Wüthrich:** explainable RL, multi-agent strategy and eventual RL-plus-MPC architecture.
- **PlaNet/Dreamer/TD-MPC2/Iso-Dream:** later latent dynamics and planning, after transparent and calibrated prerequisites.

A paper reference in a design document is not implementation progress. Progress begins when the claim, equations, tests and tolerance are executable.

# 11. Scientific and numerical standards

## 11.1 Units and coordinates

- Use SI units internally unless a contract explicitly states otherwise.
- Put unit suffixes in ambiguous names or type/document them centrally.
- Normalize only at model boundaries; retain physical-unit artifacts.
- Define coordinate handedness, heading convention, curvature sign and track-distance origin.
- Store conversion tests for km/h, m/s, degrees/radians, milliseconds/seconds and energy units.

## 11.2 Numerical methods

- Document timestep and integration scheme.
- Perform timestep-convergence checks before calibration.
- Detect NaN, infinity, discontinuity and impossible-state propagation at the earliest boundary.
- Never hide instability with broad clipping. When clipping is required by a real constraint, log its frequency and magnitude.
- Compare analytic, automatic and finite-difference gradients when optimization depends on them.

## 11.3 Parameter discipline

Every nontrivial constant must be one of:

- physically sourced;
- paper sourced;
- calibrated from training evidence;
- a declared prior;
- a synthetic fixture parameter.

No unexplained “magic constants” may enter production. Parameter names, units, bounds, provenance and sensitivity belong in configuration or a parameter registry.

## 11.4 Calibration versus validation

- Calibration selects parameters.
- Validation estimates generalization.
- Benchmarking compares frozen systems.

Do not use the same session for all three. Do not repeatedly inspect and retune against the untouched benchmark.

# 12. Machine-learning standards

## 12.1 Mandatory baseline ladder

Use the strongest applicable subset of:

1. previous value / previous lap;
2. constant velocity or acceleration;
3. transparent deterministic physics;
4. linear or ridge regression;
5. tree ensemble such as XGBoost;
6. interpretable state-space model;
7. GRU/LSTM/SSM/TFT;
8. latent world model;
9. current production APEX model.

A larger model is rejected when it does not add meaningful held-out or closed-loop value.

## 12.2 Fair comparison

Comparisons must align:

- input information;
- prediction target;
- horizon;
- autoregressive or teacher-forced mode;
- train/validation/test events;
- data preprocessing;
- evaluation masks;
- compute or parameter budget when relevant.

Do not compare one-step ridge accuracy to eight-step autoregressive GRU accuracy as if they were the same task.

## 12.3 Required metrics

Depending on the component, report:

- MAE and RMSE in physical units;
- relative or symmetric percentage error where stable;
- error by horizon;
- section, stint, compound, track, weather and traffic breakdowns;
- interval coverage and sharpness;
- closed-loop completion and constraint violation;
- state drift;
- OOD detection performance;
- runtime and memory.

## 12.4 Explanations

Feature importance or counterfactual plots must be tested for faithfulness. A visually attractive explanation is not evidence.

# 13. Strategy and optimizer safety

Planning amplifies model errors. Therefore:

1. Validate the forward model before optimizing through it.
2. Establish a trusted horizon and support region.
3. Implement a simple rule and exact tiny oracle first.
4. Test optimization with known synthetic optima.
5. Add penalties or constraints only for real requirements, not to conceal failures.
6. Deliberately search for planner exploitation.
7. Re-evaluate candidate strategies in higher-fidelity or independent models.
8. Use uncertainty-sensitive ranking and robust objectives.
9. Fall back or abstain when scenarios are out of support.

No strategy recommendation should be called optimal unless it is optimal under a fully specified model and solver tolerance. In other contexts, use terms such as best evaluated, lowest estimated race time or lowest regret against the available benchmark.

# 14. Future game telemetry contract

When the game is purchased, it becomes a **separate experimental domain**, not APEX’s reality oracle.

## 14.1 Permitted role

Game telemetry may test:

- step response to throttle and braking;
- curvature/speed/steering relationships;
- DRS and fuel-mass directionality;
- tyre temperature, energy and wear relationships;
- compound crossover;
- ERS deployment and harvesting;
- pit loss, inlap/outlap and undercut scenarios;
- planner response under scripted interventions;
- domain shift between public data and game physics.

## 14.2 Required process

Before collecting game evidence:

- freeze the schema in `apexsim.research.game_validation`;
- pre-register scenarios, inputs, metrics and tolerances;
- preserve raw telemetry and game settings;
- distinguish assists, setup, weather, damage and AI level;
- do not retune on the evaluation scenario without recording a new calibration split;
- report directional agreement separately from magnitude agreement;
- compare public-data, APEX and game results side by side.

## 14.3 Forbidden inference

A match to the game does not prove a match to a real F1 car. A mismatch does not automatically make the public-data model wrong. It is evidence about cross-domain consistency.

# 15. Code and repository standards

## 15.1 Every implementation change must include

- a clearly scoped backlog or issue identifier;
- type hints for public interfaces;
- docstrings for assumptions, units and side effects;
- configuration rather than hidden constants;
- deterministic seed handling where applicable;
- unit tests;
- one integration or artifact-level test when behaviour crosses modules;
- failure messages that identify the earliest broken contract;
- documentation or an ADR when architecture changes;
- a reproducible command and expected output location.

## 15.2 Test pyramid

1. Hand-calculated equation fixtures.
2. Unit and invariant tests.
3. Property and boundary tests.
4. Module integration tests.
5. Deterministic vertical-slice tests.
6. Public-data replay tests.
7. Statistical evaluation tests with tolerances.
8. Planner red-team tests.

Do not rely only on end-to-end tests; they make root causes difficult to locate.

## 15.3 Determinism

With fixed inputs, configuration, seed and software version:

- deterministic modules should match exactly or to a declared numerical tolerance;
- stochastic modules should reproduce sampled streams where designed to do so;
- artifact manifests must record seed and configuration;
- hidden global random state is prohibited.

## 15.4 Artifact immutability

A completed run should create a new directory containing:

- configuration snapshot;
- data manifest;
- code/commit identifier when available;
- environment and dependency information;
- model/component versions;
- metrics;
- predictions or rollouts;
- quality report;
- warnings and constraint projections;
- human-readable summary.

Do not overwrite a prior run silently.

# 16. Definition of done

A task is not done because code exists or tests compile. It is done only when:

1. Dependencies were satisfied.
2. Scope and assumptions are documented.
3. The implementation is connected through a stable interface.
4. Unit and integration tests pass.
5. The acceptance gate in the backlog passes.
6. Baselines were compared fairly.
7. Required artifacts were generated and inspected.
8. Limitations and failure cases are recorded.
9. Documentation and backlog status are updated.
10. A rollback path exists.

Backlog status meanings:

- `TODO`: not started or no valid evidence.
- `IN_PROGRESS`: active work; gate not yet passed.
- `BLOCKED`: dependency or evidence unavailable.
- `INCONCLUSIVE`: implementation ran, but evidence cannot support a decision.
- `DONE`: acceptance gate passed and artifacts are present.
- `REJECTED`: investigated and intentionally not promoted.

Never set `DONE` merely because an AI generated the files.

# 20. Forbidden shortcuts

The following actions violate this guide unless formally approved and documented:

- random timestamp splits for temporal race data;
- fitting normalizers on validation or test events;
- using future pit, flag, outcome or control values as unintended inputs;
- calling proxy tyre energy measured tyre energy;
- hardcoding constants for one track without configuration and provenance;
- evaluating only a training circuit;
- reporting only aggregate error while hiding failed regimes;
- replacing physical states with opaque latent values without probes and fallback;
- adding RL before an exact/rule/optimization baseline;
- adding a planner before model-exploitation tests;
- silently clipping invalid state to make a run finish;
- tuning against the untouched benchmark or future game evaluation set;
- presenting deterministic predictions without uncertainty when stochasticity matters;
- marking tasks complete without acceptance artifacts;
- refactoring broad areas during a scientific experiment without a matched baseline;
- optimizing visual polish while foundational P0 gates are open.

# 21. Progress reporting

Measure progress using evidence, not activity.

A useful progress report contains:

- maturity level before and after;
- backlog IDs completed, rejected or blocked;
- tests added and passing;
- datasets and manifests created;
- baseline versus new metrics;

- artifact paths;
- known limitations;

# 22. Release criteria for a 10/10 real-world-oriented simulator

APEX reaches the intended R10 standard only when all of the following are true:

- a multi-season, multi-track public benchmark is frozen;
- raw data provenance and legal constraints are documented;
- track, vehicle, tyre, fuel and energy subsystems are calibrated and validated independently;
- complete unseen laps and races remain stable in closed loop;
- full-field stochastic outputs match held-out timing and event distributions within declared tolerances;
- strategy systems beat fixed and rule-based baselines and report regret against strong oracles where possible;
- uncertainty intervals are calibrated and used in decisions;
- OOD detection, fallback and abstention are tested;
- paper-derived components have equation maps and replication/adaptation reports;
- future game experiments are reported as a separate domain-shift campaign;
- planner exploitation and adversarial scenarios have been red-teamed;
- all major claims have reproducible commands, artifacts, model cards and dataset cards;
- unsupported regions are explicitly documented.

A high-quality simulator is not one that is never wrong. It is one that quantifies where it is likely to be wrong and refuses to overclaim.

---

# 23. Immediate direction from the delivered kit

The delivered repository already provides:

- deterministic fixtures and a runnable multi-car vertical slice;
- public-source adapters and canonical telemetry scaffolding;
- transparent vehicle, track, tyre, weather, race and strategy modules;
- GRU, SSM and RSSM educational/experimental implementations;
- paper registry and paper-to-code protocols;
- FIENI-style strategy, tyre-energy proxy forecasting and latent tyre-state starters;
- a future game-validation contract;
- a research backlog through R10.

The correct next movement is **deeper evidence, not wider feature count**:

1. finish R1 equation fidelity and exact tiny-case checks;
2. freeze public-data manifests and untouched benchmarks;
3. calibrate and validate single-car replay;
4. establish stable closed-loop laps;
5. deepen tyre/fuel/ERS models;
6. calibrate stochastic full-field behaviour;
7. add adaptive strategy systems against strong oracles;
8. only then build multi-agent latent planning;
9. later use the game for pre-registered cross-domain tests;
10. freeze the public benchmark and release evidence.

This sequence is the central guarantee that a 10/10 starting kit can mature toward a 10/10 real-world-oriented simulator rather than becoming an impressive but unvalidated demo.

# 24. Final instruction

When uncertain about what to do next, choose the task that most improves one of:

- correctness;
- identifiability;
- calibration;
- held-out validation;
- uncertainty;
- closed-loop stability;
- reproducibility;
- comparability to a strong baseline.

Do not choose the task that merely makes APEX look more complete.
